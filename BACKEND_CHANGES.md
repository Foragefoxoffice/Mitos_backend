## 2026-09-23 (2)

- New `src/utils/phoneNumberLookup.js` (+ `.test.js`), `src/controllers/salesAgentController.js` — **The most significant bug found this session.** User reported a campaign test message showing "there" for every variable, including the recipient's own name, not just the Mark Booster ones. Investigated by querying prod directly: `user.phoneNumber` is stored inconsistently across the real userbase — 15,542 of 15,675 rows (99.2%) as E.164 `+91XXXXXXXXXX`, a legacy ~133 rows as a bare 10-digit number with no country code — but WhatsApp always delivers the sender's number normalized to digits-only with no `+` (e.g. `919913087772`, via `sendWhatsappOTP.normalizePhone`). Both `buildUserSalesContext` (the function that runs on **every single inbound WhatsApp message** to fetch the sender's account) and `sendCampaignToRecipient`'s recipient lookup did an exact-match `prisma.user.findUnique({ where: { phoneNumber } })` against that normalized value — which silently returns `null` (no error, no crash) for the `+91`-prefixed 99.2% majority. Confirmed directly: an exact-match query for a real user's normalized number (`919913087772`) returned `null`, while their actual stored value was `+919913087772`. **This means the AI has likely been treating almost every real customer as an unrecognized/anonymous user for this entire MVP's life** — no trial/premium status, no name, no Mark Booster analytics — not because of any earlier bug already found and fixed, but because the account match itself was silently failing underneath all of it. New `buildPhoneNumberLookupCandidates(normalizedPhone)` (pure, tested) builds the small set of formats a given normalized number could appear as (digits-only, `+`-prefixed, and — if 12 digits starting with `91` — the bare 10-digit legacy form) and a new `findUserByPhoneNumber(normalizedPhone, extraArgs)` queries `phoneNumber: { in: candidates }` instead of an exact match. Both known call sites switched over. Verified against production data directly (not just unit tests): the new candidate-based lookup correctly found a real user (`Vanshika m. Patel`, stored as `+919913087772`) that the old exact-match lookup returned `null` for. All 14 Jest suites / 129 tests pass (4 new). **This is a live behavior change on the single most-used code path in the sales agent — deploy and monitor real conversations closely after this one.**
