# Backend Changes Log

Running notes of changes made to files in this `backend/` directory. Newest entries at the top.

## 2026-08-28

- `src/controllers/aiController.js` — `buildGeneralUserContext` now also fetches `user.className` (Class 11/Class 12/Repeater) and includes it in the context sent to ai-service for the general "Ask Mitos AI" Home-screen chat, mapped to a readable label via new `CLASS_NAME_LABELS`. Companion to ai-service commit `dfc487e`, which broadened that chat mode from "only answer questions about the student's own app data" to "also answer real NEET Physics/Chemistry/Biology study questions" — this lets it pitch those answers at the student's actual class level instead of guessing or mixing 11th/12th content indiscriminately.

- `src/controllers/aiController.js` — `sendChatMessage`'s call to ai-service (`aiServiceClient.post("/internal/ai/chat/message", ...)`) now overrides the client's global 15s timeout with 60s, matching the mobile app's own 60s timeout on `sendChatMessage` (see `mitoslearning/src/utils/api.js`). Root cause of a live reported bug: a real "complex"-tier chat reply (e.g. "Explain this question step by step") can legitimately take 15-20+ seconds even on the fastest AI provider — live-measured at 16.2s during this investigation — so the old 15s backend timeout gave up on ai-service *before* ai-service had actually finished. The student saw "Something went wrong," but ai-service kept running in the background and (after the companion fix in ai-service commit `44b79d7`, which defers writing a chat message row until the AI call actually succeeds) eventually wrote a real, credit-consuming success the student never got to see delivered — then their manual retry burned a second credit for the reply they actually received. Reproduced twice live via screenshots, both on the "step by step" complex prompt specifically. This fix, combined with ai-service commit `fdbbba3` (bounding every individual AI provider's own timeout to 30s instead of an unbounded/10-minute SDK default, so a single stuck provider can't itself blow past this 60s budget), closes the timing mismatch for the realistic case. Verified live: a real complex-tier DeepSeek call completed in 1.2-16.2s across repeated tests (varies per call), comfortably inside both the new 60s backend timeout and each provider's 30s cap.

- `src/controllers/notificationController.js`, `admin/src/pages/admin/SendNotification.jsx`, `admin/src/pages/admin/AppSettings.jsx` — Rebuilt the admin "Send Notification" recipient-targeting system after confirming a real, live bug: one trial user (10 days into a still-active trial) received 80 admin notifications in 14 days, the same ~6-message batch re-sent every day. Root cause: the existing "skip anyone who already got this exact message" dedup only applied when `recipientMode === 'date'` — any other send type (in particular "By Status → Trial Users") had zero memory of who'd already been notified, so a daily re-send of the same campaign to "all active trial users" (74 people) just kept re-notifying everyone with no cap, forever. Three fixes: (1) the dedup check now runs unconditionally for every send type, not just date-mode. (2) Added a new admin-editable (via `appsetting` key `notification_daily_cap_per_user`, default 5, same generic-settings pattern as AI Chat's caps) hard per-user daily notification cap, independent of the dedup check, as a backstop against any future bug/misuse of this kind. (3) "By Date" sends (e.g. "trial ending in next 3 days") now have their recipient list recomputed by the backend itself, fresh, from `trialStartedAt`/`trialEndsAt`/`premiumExpiry` at the moment Send is clicked (new `buildDateFilterWhere` helper) — the admin frontend now sends `dateField`/`condition`/`days` instead of a pre-computed `userIds` array, removing the risk of a stale browser tab (holding a user list from whenever the page last loaded) silently sending to the wrong set. Verified live against real data: the new server-side filter for "trialEndsAt, in next 3 days" returns exactly 36 users, matching the admin UI's own live preview count exactly; for comparison, ALL currently-active-trial users (the likely actual recipient set behind the bug) is 74 — almost double, consistent with the reported "sends to all trial users" symptom. Also verified the dedup and daily-cap checks both correctly flag the real spammed user (id 15576) as "already notified" / "over today's cap" against the actual notification history that caused this investigation. Response payload now also reports `skippedAlreadyNotified`/`skippedDailyCap` counts, surfaced in the admin UI's success message for visibility. The `notification_daily_cap_per_user` setting also got an admin-facing control — a new "Notifications" card on the App Settings page (`AppSettings.jsx`), same load/save wiring as the existing "AI Chat Credits" card — so it's editable without a direct DB write.

- `src/controllers/authController.js` — Apple App Review asked for an expired-premium account and a plain registered account in addition to the existing premium demo login, so the single hardcoded `DUMMY_TEST_NUMBER`/`DUMMY_TEST_EMAIL` bypass became `DUMMY_TEST_ACCOUNTS`, a map of phone number → `{ email, name, seed }`. Same OTP-bypass mechanism as before (fixed `123456`, no real SMS), now covering 3 numbers: `+919844444455` (existing premium demo, `seed: null` so its state stays whatever it's manually set to), `+919844444456` (expired premium — seeded `status: SUSPENDED, premiumExpiry: null`, matching what `cron/expireSubscriptions.js` does to a real expired user, which `SubscriptionScreen.jsx` in the mobile app renders as an explicit "expired" state), `+919844444457` (plain registered/free — `status: REGISTERED`, no premium/trial history). Unlike the original which only seeded state on first account creation, `verifyWhatsappOtp` now re-applies a non-null `seed` on every login, so a reviewer's in-app actions (e.g. triggering a real purchase) during one review round can't leave the account in the wrong state for the next round. Verified live: both new numbers create/log in correctly via the real `sendWhatsappOtp`/`verifyWhatsappOtp` handlers, and re-logging in after manually drifting `+919844444456` to `PREMIUM` correctly snapped it back to `SUSPENDED`/`premiumExpiry: null`.

## 2026-08-27

- `src/controllers/aiController.js` — Fixed intermittent "Something went wrong. Please try again in a moment." on AI Chat, confirmed live: `ai-service` was being restarted repeatedly today (during an unrelated dictionary-cleanup task) and any chat request that landed during the few-hundred-ms-to-several-second restart gap got a connection-refused error with no retry, surfacing directly to the student. Added a `withRetry()` helper — retries up to 2 times (700ms apart) but ONLY on connection-level errors with no `error.response` at all (`ECONNREFUSED`/`ECONNRESET`/`ENOTFOUND`/`EHOSTUNREACH`), meaning ai-service never received the request in the first place, so retrying is safe with zero risk of double-processing. A real error response from ai-service (daily cap exceeded, a genuine 500, etc.) or a timeout (`ECONNABORTED` — ai-service may have already received and be acting on the request) is deliberately NOT retried, to avoid duplicate chat messages or double-counting a message against the daily cap. Applied to `sendChatMessage` (POST, the one that matters most since it mutates state) and `getChatHistory`/`getChatQuota` (GET, safe to retry unconditionally but kept to the same criterion for consistency). Companion change: `ai-service` now runs under PM2 (`ecosystem.config.js`, previously only used as a template, never actually running) instead of a manually-run `node server.js` — cuts the restart gap itself from ~5s+ (manual kill + sleep + relaunch) to ~0.2-0.3s (measured live via a health-check poll during a real `pm2 restart`), on top of the retry logic above.

## 2026-08-19

- `src/controllers/aiController.js` — `sendChatMessage` fixed two bugs in how AI Chat builds question context. (1) It always queried the main `question` table regardless of where the question actually came from — but Favorites merges rows from `question` ("mock") and the separate `testseriesquestionbank` table ("test-series"), which have independent autoincrement PKs, so the same numeric `questionId` can be a completely different question depending on source. A student asking about a Test Series Biology question was getting an answer built from an unrelated Physics mock question that happened to share the id. Now branches on a new `sourceType` field ("mock"/"test-series") the client sends, querying the matching table. (2) The context payload never included `portion` or `questionType` even for the correct table/question — both are now included (`prisma.question`/`testseriesquestionbank` `include`) and threaded through to the AI prompt (`ai-service/src/prompts/chatPrompt.js`). Companion changes: `ai-service/src/services/chatService.js` (chat sessions are now namespaced by source too — same collision risk existed for `ai_chat_session`, which only keys on `(userId, questionId)`; test-series ids are stored negated to keep them in a disjoint range from mock ids, avoiding a schema migration), `ai-service/src/controllers/chatController.js` (threads `source` through), `mitoslearning/src/utils/api.js`, `mitoslearning/src/screens/AiChatScreen.jsx`, `mitoslearning/src/components/Favorites/FavoriteQuestionCard.jsx` (passes `sourceType` based on `_source`).
- `src/controllers/notificationController.js` — `sendNotification` now skips users who already received a notification with the same raw `message` when the request has `recipientMode: 'date'` (set by admin's "By Date" send flow). Fixes a confirmed live bug: the "By Date" filter (e.g. "trial ends in next N days") is a stateless rolling window re-evaluated on every send, so re-running the same date-based broadcast on consecutive days kept re-matching — and re-notifying — students still inside the window. Verified one user received the identical "Trial Ends Today" notification 8 days in a row (Aug 10–19) before this fix. Scoped to date-filtered sends only — "All Users"/"By Status"/"Specific Users" sends are unaffected. Companion change in `admin/src/pages/admin/SendNotification.jsx` (sets `recipientMode: 'date'` on the payload).
