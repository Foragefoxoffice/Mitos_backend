## 2026-09-16

- New `src/utils/salesRecipientCandidates.js` (+ `.test.js`), `src/controllers/salesAgentController.js`, `src/routes/salesAgentRoutes.js` — New `GET /api/sales-agent/admin/recipient-candidates` (`verifyAdmin`-gated) endpoint, the recipient-selection backend for the campaign-broadcast admin UI's By Status / By Date filters (the search-by-name/email/phone endpoint from 2026-09-15 (8) and this segment-pull endpoint are two different ways to build up a recipient list before hitting the (9) send endpoint). Pure where-builder `buildRecipientCandidateWhere` (unit-tested, 6 cases) takes `{ filterType: 'status'|'date', status, field, condition, days, includeContacted, now }`: `status` mode filters on the given `UserStatus` value directly; `date` mode delegates to the existing `buildDateFilterWhere` (`dateFilter.js`, already used by the notification broadcast feature) so the `today`/`in_next`/`expired_within`/`exactly_days_ago` conditions and their IST-anchored day-boundary logic aren't duplicated. Either mode always additionally excludes `status: DELETED` users and anyone with no `phoneNumber` (unreachable over WhatsApp regardless of segment). By default also excludes any user who already has a `whatsappconversation` row (`whatsappConversations: { none: {} }`) — i.e. anyone the sales agent has ever contacted before, whether via owner testing or a prior campaign — so pulling the same segment again naturally surfaces only people not yet reached, without the admin having to manually track who's already been sent to. A new `includeContacted=true` query flag opts back into the full segment (deliberate re-sends). Controller (`getRecipientCandidates`) paginates (`page`/`pageSize`, capped at 100 per page to match the existing per-send `MAX_CAMPAIGN_RECIPIENTS` cap from `salesCampaignHelpers.js`), returns `{ users: [{id, name, phoneNumber}], totalMatching, page, pageSize }`, and 400s on an invalid/missing filter (unrecognized `filterType`, `status` mode with no `status` given, or an invalid `date` mode field/condition per `buildDateFilterWhere`'s own `VALID_DATE_FIELDS` check). Since the actual send is already hard-capped at 100 recipients per campaign regardless of segment size, this is what makes browsing/sending a segment larger than 100 in successive batches practical — each subsequent pull of the same filter naturally shows the next batch of people who haven't been reached yet, instead of the same top-100 every time.

## 2026-09-15 (10)

- `src/controllers/salesAgentController.js`, `src/routes/salesAgentRoutes.js` — New `GET /api/sales-agent/admin/campaigns` (`verifyAdmin`-gated) read-only endpoint listing past WhatsApp campaign sends. Returns up to 50 most recent `salescampaign` rows (newest first), ordered by `createdAt` desc. Response shape: `{ campaigns }`. ## 2026-09-15 (9)

- `src/controllers/salesAgentController.js`, `src/routes/salesAgentRoutes.js` — New `POST /api/sales-agent/admin/campaigns` (`verifyAdmin`-gated) — the actual WhatsApp campaign send, the piece the template-fetch (7) and user-search (8) endpoints were prep for. Request body is `{ templateName, templateLanguage, recipients: [{ userId? , phoneNumber, forceResend? }], forceResend? }`. Validates recipient count against the 100 cap via `validateCampaignRecipients` (`MAX_CAMPAIGN_RECIPIENTS`, from `salesCampaignHelpers.js`) before anything else. Never trusts a client-submitted template blindly: re-fetches the live approved-template list via `fetchApprovedTemplates()` (Meta Graph API, same helper as (7)) and matches on `name`+`language` server-side — a client claiming an unapproved/nonexistent template is rejected with 400, and a template requiring more than one body variable is rejected outright (the fill-in logic only supports one). Per-recipient send (`sendCampaignToRecipient`, internal only, not exported) fills that one body variable with the recipient's name via `buildTemplateBodyComponents`, forwarded through `sendTemplateMessage`'s newly-added `components` param. Dedupes against the same template going to the same number within 7 days via `buildCampaignDedupeWhere` (queries `whatsappmessage` by phone+template text+7-day window) unless `forceResend` is set per-recipient or globally. Batches sends via `sendInBatches` (`src/utils/batch.js`, from the 2026-09-11 FCM-502 fix) at `CAMPAIGN_BATCH_SIZE = 5` concurrent — deliberately conservative given each iteration does multiple DB round-trips plus a live WhatsApp API call, to avoid the kind of unbounded-`Promise.all` OOM/502 this codebase hit before on FCM sends. Creates/updates a `whatsappconversation` for each recipient via the existing `ensureSalesConversation` — which is what makes them eligible for AI auto-replies once they reply, per (6)'s reply-gate generalization (a stranger texting in is still ignored; a campaign recipient now has a conversation row on record, so their reply is eligible). Creates a `saleslead` at stage `CONTACTED` only if one doesn't already exist for that conversation — a repeat campaign to someone who already replied and progressed further (e.g. `NEGOTIATING`) doesn't regress their lead stage back to `CONTACTED`. Creates a `salescampaign` row up front (new Prisma model, migration already applied outside this task) to track `totalTargeted`, then updates it with final `sentCount`/`skippedCount`/`failedCount` after the batched send completes; each per-recipient `whatsappmessage` row is tagged with the new nullable `campaignId` column for later per-campaign drill-down. Both the campaign-row and per-message writes tolerate a not-yet-migrated DB the same way the rest of this controller does (`isMissingSalesTableError`), though in this case the migration is already live. Response: `{ campaignId, templateName, sentCount, skippedCount, failedCount, results: [{ phoneNumber, status, error? }] }`. This endpoint is integration-level (live WhatsApp send, live Meta template fetch) and is verified manually via a real curl call rather than unit tests — no new test files in this change; `salesCampaignHelpers.js`/`whatsappTemplates.js`/`batch.js` (all pre-existing, imported not modified) already carry their own unit tests. This is the send half of the admin campaign-broadcast feature; the recipient-picking/UI half is separate admin-panel work.

Root cause: FCM pushes were fired via a single unbounded `Promise.all` over every matched recipient at once — for ~16k users that's ~16k concurrent `admin.messaging().send()` calls in one request, in a process running as a single PM2 fork-mode instance capped at `max_memory_restart: "500M"` / `--max-old-space-size=512` (`ecosystem.config.js`). Fix: new `sendInBatches(items, batchSize, worker)` (unit-tested, including a concurrency-bound assertion) processes the FCM fan-out in fixed-size batches (`FCM_SEND_BATCH_SIZE = 250`), each batch's `Promise.all` awaited before the next starts, so memory stays flat regardless of recipient count. Response shape (`delivered`/`noToken`/`invalidToken`/`failedOther`) and per-recipient behavior are unchanged — this only bounds concurrency, large sends just take longer wall-clock time now instead of risking a crash. Not yet re-verified against a live ~16k-user send (would require redeploying to production first) — recommend testing on a smaller "By Status" segment before repeating the full-population resend.
